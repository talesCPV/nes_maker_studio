Ponto 3 — isso é o ponto crítico que você pediu pra eu sinalizar

Hoje o projeto inteiro (cabeçalho da ROM, nrom.cfg, o .asm gerado) assume Mapper 0 (NROM), que tem CHR-ROM fixo de 8KB — sem troca de banco nenhuma. O PPU realmente só enxerga 2 páginas de 4KB por vez ($0000-$1FFF), mas com NROM essas 2 páginas são o CHR inteiro da ROM, gravado de uma vez só; não existe "escolher qual banco fica ativo" em tempo de execução.

Se a CHR tiver 4 páginas (2 bancos = 16KB), isso não cabe mais num NROM. Pra "fase 1 usa banco 1, fase 2 usa banco 2" funcionar de verdade rodando no console, a ROM precisa de um mapper com troca de banco de CHR, tipo o CNROM (mapper 3) — o mais simples que existe pra isso: um registrador simples (escrita em qualquer endereço de 
8000−
8000−FFFF) troca qual banco de 8KB de CHR está visível, PRG continua fixo. Isso é uma mudança que afeta o build-rom.js/nrom.cfg inteiro (cabeçalho, config do ld65), não só o level-design.

Do jeito que a arquitetura já foi desenhada nas últimas mensagens, três coisas precisam de um lar: Variáveis, Eventos e as Regras (quando X, faça Y). Dá pra ser um módulo só na barra lateral (ex: 🧠 Lógica ou 📜 Programação) com essas três abas internas — do mesmo jeito que o Backgrounds já tem sub-painéis (Pintar/Hitbox/Texto) dentro de um módulo só. Isso evita poluir a barra lateral com 3 itens nova, e mantém tudo que é "cérebro do jogo" junto num lugar.

Como eu NÃO desenharia isso: editor visual de blocos/fluxograma

Sei que é tentador pensar em algo tipo Scratch (blocos que encaixam, arrastar linhas conectando nós) — é bonito e "parece" mais amigável. Mas isso é um projeto de engenharia de front-end enorme por si só (drag-and-drop, snapping, redimensionamento, serialização de grafo, zoom/pan de canvas...), e olhando o que já construímos, nosso padrão sempre foi formulário estruturado + lista (select de fase, lista de metatiles, lista de warps) — nunca canvas livre. Eu ficaria fiel a esse padrão aqui também: menos risco, mais rápido de entregar, e consistente com o resto do sistema.

O formato que eu proporia: lista plana de instruções, não árvore

Aqui vai uma simplificação importante que acho que vale a pena adotarmos de propósito: em vez de "blocos aninhados" (SE dentro de SE dentro de loop), cada Regra é uma lista sequencial e plana de instruções, incluindo uma primitiva de salto condicional — exatamente como o próprio 6502 pensa:

Regra "cursor_menu_desce":
  1. SE evento = Botão Baixo pressionado
  2. SE cursor_pos < total_itens - 1        -> senão PULE pra linha 5
  3. SOMA cursor_pos, 1
  4. TOCA som_bip
  5. (fim)

Isso mapeia quase 1:1 pra ASM (cada linha vira poucas instruções 6502, sem precisarmos de parser de árvore nem resolver precedência de expressão). O "compilador" fica sendo, na prática, um tradutor linha-a-linha — muito mais parecido com o que já fazemos no build-rom.js hoje (gerar bloco de ASM a partir de dado estruturado) do que com escrever um compilador de verdade. Aninhamento profundo (loop dentro de loop dentro de condicional) é exatamente o que você mesmo apontou como perigoso lá atrás — com lista plana + saltos, a gente simplesmente não abre essa porta.

Esboço do modelo de dado
js
Project.data.variables = [
  { id, name, type: 'bool'|'byte'|'word', zeroPage: bool }
]
Project.data.events = [
  { id, name, category: 'input'|'hitbox'|'custom', builtin: bool }
  // builtin: true pros que já vêm prontos (Cima/Baixo/A/B/Start, hitbox Dano/Warp/Plataforma)
  // builtin: false pros que o usuário criar do zero
]
Project.data.rules = [
  {
    id, name,
    scope: 'global' | { phaseId },   // regra vale o jogo todo, ou só numa fase
    steps: [
      { type:'if_event', eventId, elseGotoStep },
      { type:'if_var', varId, op:'>', value, elseGotoStep },
      { type:'set_var'|'add_var'|'sub_var', varId, value },
      { type:'action', actionId, params }  // primitivas: tocar som, ir por warp, etc
    ]
  }
]

Isso resolve exatamente sua preocupação com "posso criar novos eventos": a lista de eventos fica editável pelo usuário (builtin:false), e como ela vive junto das Regras (que referenciam eventId por id, não por nome fixo), um evento customizado funciona igual a um builtin no resto do sistema — sem precisarmos prever categorias.

Onde eu começaria a implementação de verdade

Nessa ordem, porque cada peça é pré-requisito da próxima:

Aba Variáveis — é a mais isolada (não depende de nada), e já valida o empacotamento de bits que você propôs (bool compartilhando byte).
Aba Eventos — cadastro simples (nome + categoria), builtin pré-populado com os de input/hitbox que já existem no projeto.
Aba Regras — a UI de "lista de passos" por regra, ainda sem gerar ASM nenhum (só validando que o dado fecha).
Só depois entra o build-rom.js aprendendo a traduzir isso — e essa parte só faz sentido depois que a fundação de loop principal + leitura de input (que discutimos na mensagem anterior) já existir de verdade.
